Если хотите, я могу ещё показать одну очень полезную вещь для этого проекта:

👉 идеальную SQL схему таблицы orders, которая сильно упрощает worker и предотвращает несколько неприятных race conditions.




Хорошо. В этом проекте таблица orders — центральная, и от её схемы зависит:

простота работы worker

отсутствие race conditions

корректное начисление баллов

удобные запросы

Я покажу практичную схему, которую обычно используют для этого задания.

1. Таблица users
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    login TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT now()
);

Почему так:

BIGSERIAL — стандарт для id

login UNIQUE — чтобы нельзя было зарегистрировать одинаковые логины

пароль хранится только как hash

2. Таблица orders

Это самая важная таблица.

CREATE TABLE orders (
    number BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    status TEXT NOT NULL,
    accrual DOUBLE PRECISION,
    uploaded_at TIMESTAMP NOT NULL DEFAULT now()
);

Разберём поля.

number
number BIGINT PRIMARY KEY

Почему PRIMARY KEY:

номер заказа уникальный

удобно искать

Это позволит быстро проверять:

существует ли заказ
user_id
user_id BIGINT REFERENCES users(id)

Это связь:

user 1 -> many orders
status
status TEXT NOT NULL

Возможные значения:

NEW
PROCESSING
INVALID
PROCESSED

Это статусы из ТЗ.

accrual
accrual DOUBLE PRECISION

Баллы, полученные от внешнего сервиса.

Может быть:

NULL

пока заказ не обработан.

uploaded_at
uploaded_at TIMESTAMP DEFAULT now()

Нужно для:

GET /api/user/orders

ТЗ требует сортировку по времени загрузки.

3. Таблица withdrawals
CREATE TABLE withdrawals (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    order_number BIGINT NOT NULL,
    sum DOUBLE PRECISION NOT NULL,
    processed_at TIMESTAMP NOT NULL DEFAULT now()
);
order_number

Номер заказа, по которому списали баллы.

ТЗ требует:

order
sum
processed_at
4. Индексы (очень желательно)

Для worker.

CREATE INDEX idx_orders_status ON orders(status);

Worker будет делать запрос:

SELECT * FROM orders
WHERE status IN ('NEW','PROCESSING')

Без индекса это будет медленно.

5. Очень важная проверка из ТЗ

В ТЗ есть требование:

если заказ уже загружен другим пользователем — вернуть 409

Для этого нужен такой запрос:

SELECT user_id FROM orders WHERE number=$1

Если:

нет записи → можно вставить
есть запись и user_id тот же → 200
есть запись и user_id другой → 409
6. Как worker будет брать заказы

Worker делает:

SELECT number FROM orders
WHERE status IN ('NEW','PROCESSING')
LIMIT 10;

После чего:

GET /api/orders/{number}

в accrual system.

7. Обновление заказа

Когда приходит ответ:

{
 "order":"12345",
 "status":"PROCESSED",
 "accrual":500
}

worker делает:

UPDATE orders
SET status=$1, accrual=$2
WHERE number=$3
8. Как начисляются баллы

Когда статус:

PROCESSED

нужно:

добавить accrual к балансу пользователя

Но баланс обычно не хранят в таблице users.

Лучше считать его запросом:

SUM(accrual) - SUM(withdrawals)
9. Запрос баланса
SELECT
    COALESCE(SUM(accrual),0)
FROM orders
WHERE user_id=$1 AND status='PROCESSED'

и

SELECT
    COALESCE(SUM(sum),0)
FROM withdrawals
WHERE user_id=$1

11. Очень полезное улучшение (рекомендую)

Добавить уникальность списания заказа.

ALTER TABLE withdrawals
ADD CONSTRAINT unique_withdraw_order UNIQUE(order_number);

Чтобы нельзя было списать один заказ дважды.

12. Реальный production-лайфхак

Я бы сделал статус ENUM:

CREATE TYPE order_status AS ENUM (

    'PROCESSED'

И таблицу:

Это защищает от ошибок.
